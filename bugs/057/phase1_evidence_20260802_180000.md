## Key Findings (Phase 1 Evidence)

| Observation | Implication |
|-------------|-------------|
| **Local migration: ~3-4 min** | Fast on single-node v26.2.1 |
| **Cloud migration: ~5.5 min (partial 42/57 tables)** | Serverless Basic slower than local |
| **Healthz registered BEFORE migration** | Frontend serves index.html for /healthz before migration completes |
| **Fly health check: 200 OK but returns HTML** | Fly health check passes but doesn't indicate migration status |
| **FORCE_REINDEX_ON_STARTUP=true** | Reindex runs on every boot (adds time) |
| **Fly logs show no migration logs** | Migration completed in prior boot attempt (machine was killed and restarted) |
| **Current Fly machine: healthy, 1/1 checks passing** | Machine is running, healthz passes |

### Critical Insight
**The healthz endpoint returns 200 OK before migration completes** because:
1. Frontend middleware serves `index.html` for `/healthz` (SPA fallback)
2. Healthz is registered at line 105 in `server.go` — BEFORE migration runs (line 98-102 in main.go)
3. Fly's health check sees 200 OK and marks machine healthy
4. **But migration hasn't completed yet** — machine gets killed by autostop before migration finishes

**This explains the original failure:** Fly's health check passes (200 OK) but the app isn't actually ready (migration incomplete). The machine gets killed by autostop after ~5.5 min grace period, before migration completes.

## Phase 1 Conclusion

**Evidence collected successfully.** Key findings:
1. **Migration is slow on Cloud Serverless** (~5.5 min for 42/57 tables)
2. **Healthz check is misleading** — returns 200 OK before migration
3. **Autostop kills machine** before migration completes (~5.5 min vs needed ~20+ min)
3. **Local is fast** (~3-4 min) — Serverless Basic is the bottleneck
4. **FORCE_REINDEX_ON_STARTUP adds significant time**

**Ready for Phase 2A:** Single-node execution strategy experiment to determine if one-shot `ExecContext` is the bottleneck.
