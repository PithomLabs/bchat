## Phase 1: External Observability (No Code Changes)

### Goal
Collect deployment evidence from existing sources before any instrumentation.

### Actions

| Source | What to Collect | Method |
|--------|-----------------|--------|
| Fly deployment logs | Timestamps, restarts, health check failures | `fly logs -a bchat-crdb` |
| CockroachDB `SHOW JOBS` | Schema change progress, retries, duration | `cockroach sql --url "$COCKROACH_DSN" -e "SHOW JOBS"` during migration |
| Migration history | Version, completion status | `SELECT * FROM migration_history;` |
| Health endpoint timing | When `/healthz` becomes available | Shell-side `curl` loop with timestamps |
| Shell-side timing | Overall boot time, phase boundaries | `date +%s` markers in deploy script |

### Success Criteria
- Can distinguish "progressing slowly" vs "blocked/hung"
- Can identify if bottleneck is DDL execution, schema jobs, or other
- Have baseline timing for current deployment attempt

## Phase 2A: Single-Node Execution Strategy Experiment (Disposable Spike)

### Goal
Determine if one-shot `ExecContext` is the bottleneck vs per-statement execution — **without modifying production code**.

### Method (Disposable Spike)

1. Use local v26.2.1 single-node cluster
2. Reset DB to A1 (drop all tables CASCADE)
3. **Experiment A1 (One-Shot):** Run current migrator one-shot `ExecContext` via a **temporary standalone runner** that:
   - Reads `LATEST.sql`
   - Splits on semicolon
   - Executes entire file in one `ExecContext` (current behavior)
   - Measures: wall clock, per-statement latency (via replay in spike), CPU, schema jobs, retries, connections
4. **Experiment A2 (Per-Statement):** Same runner modified to:
   - Execute each statement in autocommit mode
   - Preserve tolerance strings: "duplicate column", "already exists", "column already exists"
   - Measures same metrics
5. Compare results → **discard runner**

### Per-Statement Latency Measurement (Nit 2)

Since one-shot `ExecContext` doesn't expose per-statement timings, the disposable runner will:
- Parse `LATEST.sql` into individual statements
- Execute each statement individually in a separate measurement run (replay)
- Record per-statement latency for analysis
- This is **measurement-only** — does not change the migrator behavior

### Evidence-Based Decision Criteria (Nit 1: "ETA Acceptable" Defined)

| Criterion | One-Shot Acceptable | Per-Statement Needed |
|-----------|---------------------|----------------------|
| **Progress continues** | Yes, steady | Stalls / no `SHOW JOBS` progress |
| **ETA acceptable** | Deployment expected to complete before Fly's configured deployment timeout (`--wait-timeout 45m` + healthz poll `50m`) with continuous forward progress | ETA exceeds budget |
| **No stalls** | No periods > 2 min with zero progress | Stalls observed |
| **Schema job retries** | < 5 | ≥ 5 |
| **Connection errors** | 0 | > 0 |

**Decision:** If A1 meets all "One-Shot Acceptable" criteria → keep current. If any "Per-Statement Needed" criterion met → modify `migrator.go` for Phase 2B.

## Phase 2B: Three-Node Functional Validation

### Goal
Validate chosen execution strategy on multi-region topology (functional only, not performance reproduction).

### Method
1. Create throwaway compose: 3 nodes v26.2.1 with `--locality region=aws-us-east-1/2/us-west-2`, zone-survival replication
2. Reset DB → run first-boot with chosen strategy from 2A
3. Observe: `SHOW JOBS`, progress, no crashes
4. **Not measuring:** wall clock (local ≠ Cloud per review H1)

### Success Criteria
- Migration completes without errors
- All 57 tables created
- `migration_history` = 1 row
- Vector index enabled
- No schema job failures
