## Phase 1: External Observability (No Code Changes)

### Goal
Collect deployment evidence from existing sources before any instrumentation.

### Actions

| Source | What to Collect | Method |
|--------|-----------------|--------|
| Fly deployment logs | Timestamps, restarts, health check failures | `fly logs -a bchat-crdb` |
| CockroachDB `SHOW JOBS` | Schema change progress, retries, duration | `cockroach sql --url "$COCKROACH_DSN" -e "SHOW JOBS"` during migration |
| Migration history | Version, completion status | `SELECT * FROM migration_history;` |
| Health endpoint timing | When `/healthz` becomes available | Shell-side `curl` loop with timestamps |
| Shell-side timing | Overall boot time, phase boundaries | `date +%s` markers in deploy script |

### Success Criteria
- Can distinguish "progressing slowly" vs "blocked/hung"
- Can identify if bottleneck is DDL execution, schema jobs, or other
- Have baseline timing for current deployment attempt

## Phase 2A: Single-Node Execution Strategy Experiment

### Goal
Determine if one-shot `ExecContext` is the bottleneck vs per-statement execution.

### Method
1. Use local v26.2.1 single-node cluster
2. Reset DB to A1 (drop all tables CASCADE)
3. **Experiment A1:** Run migration with current one-shot `ExecContext` (measure: wall clock, per-statement latency via split, CPU, schema jobs, retries, connections)
4. **Experiment A2:** Modify migrator cockroach arm to per-statement autocommit (preserve tolerance strings), run same migration, measure same metrics
5. Compare results

### Decision Criteria
| Metric | One-Shot Acceptable | Per-Statement Needed |
|--------|---------------------|----------------------|
| Total migration time | < 10 min | > 10 min |
| Progress steady (no stalls) | Yes | No / stalls observed |
| Schema job retries | < 5 | ≥ 5 |
| Connection errors | 0 | > 0 |

### Implementation (If A2 Chosen)
```go
// In migrator.go cockroach arm (around line 212)
// Split LATEST.sql on semicolon, execute each statement in autocommit
// Preserve tolerance strings: "duplicate column", "already exists", "column already exists"
// Add test updates for new execution path
```

## Phase 2B: Three-Node Functional Validation

### Goal
Validate chosen execution strategy on multi-region topology (functional only, not performance reproduction).

### Method
1. Create throwaway compose: 3 nodes v26.2.1 with `--locality region=aws-us-east-1/2/us-west-2`, zone-survival replication
2. Reset DB → run first-boot with chosen strategy from 2A
3. Observe: `SHOW JOBS`, progress, no crashes
4. **Not measuring:** wall clock (local ≠ Cloud per review H1)

### Success Criteria
- Migration completes without errors
- All 57 tables created
- `migration_history` = 1 row
- Vector index enabled
- No schema job failures

## Phase 4: Deploy + Verify + Close

### Deploy
```bash
task deploy:cockroach
# Resumes Cloud migration idempotently at 42/57 tables
```

### Verify (Deployment Success Checklist)
Per review recommendation — objective completion criteria:

- [ ] Machine remains healthy for **10 minutes** after startup
- [ ] Migration history shows expected version (1 row, FS version)
- [ ] No active schema jobs remain (`SHOW JOBS` returns 0 running)
- [ ] `task verify:production` passes (7/7, test tenant destroyed)
- [ ] Restart succeeds **without** rerunning migration (boot idempotency)
- [ ] Second deployment completes without timeout

### Close-out
- Flip `FORCE_REINDEX_ON_STARTUP=false` + redeploy
- Archive artifacts: `bugs/057/artifacts/deploy-attempt2/` (Fly logs, Cockroach logs, migration output, evidence doc)
- Update docs with observed timings + grace-period rationale
